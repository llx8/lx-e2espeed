# Standard pass

The user hands over a project and says to run the standard pass, then leaves or watches. You onboard it, measure it, work through the fixed catalog below without the user's picks, and report once at the end. The user asked for it on 2026-10-13: the routine part of every project (environment, baseline, the usual moves) should run without a discussion, and the promising changes that alter outputs should reach them finished, with numbers.
It is safe for the same reason as a self-iteration run: a change lands only when the outputs are identical and the gain is measured; everything else is parked for the user. Starting the pass is the user's approval of this catalog, and of nothing beyond it.

## Contract with the user
- The pass does not stop. Never end your turn for a question, a progress report, or a plan: write the question under "Waiting for the user" in STATUS.md or in the trial's "Needs the user" column, take the default below, and go on. Progress goes into STATUS.md ("In progress: standard pass (rules/standard-pass.md), item <n> of <N>") and lx-work commits, plus a short status line when the user is watching (`rules/reporting.md`), which never waits for an answer. The pass ends when every catalog item is kept, parked, or skipped with a measured reason, at the end time the user gave, or when the environment breaks (the same infrastructure error twice). The user, 2026-10-13: it must not run for a few minutes and then stop.
- Before the first command, check that the session runs the harness without permission prompts; a prompt nobody is there to answer is the one other thing that may stop the pass, and the next session resumes from STATUS.md and the queue.
- Starting the pass also covers what onboarding would ask about: `setup.sh project`, `git init` of a project that is no repo (nothing is pushed), excluding weights, and linking a sibling repo the project reads code from.
- What the user decides is listed once, in the first status line, and defaulted at once: the production GPU (default: what the deployment files say, else the shared L20, `hardware/l20.md`); the production image (the deployment files, else the previous image in `local/site.md`); calibration data (default: none, so INT8 and FP8 are skipped); scenarios and shapes (default: the repo's own test inputs or example requests, and the contract's maximum); MPS and workers (default: MPS on, one worker, as `rules/onboarding.md` assumes); the end time (default: none). Every default goes into PROJECT.md and DECISIONS.md as `<value> (pass default, not discussed)`; an answer that arrives mid-pass applies from the next item.
- Lands without asking (`exp.sh keep`): a catalog item whose outputs are L0 against the frozen references, whose gain is beyond the noise floor (or less code at equal speed), and which changes no contract in PROJECT.md. L1 lands too when the project already runs that model as a built engine at that precision and the engine-noise tool measured the L1 spread. Every other gain is parked (`exp.sh park`) with its level and what the user must decide; numeric precision and `torch.compile` may be tried this way, as in a self-iteration run, because they do not land.
- Still the user's, by parking or skipping, never by stopping: anything outside the catalog, a contract change, a dependency the target image lacks (installing is allowed only for the project's own imports, pinned to the image's versions as `local/site.md` says), a change to the baseline or the references, and any difference beyond L0.
- Every other rule holds: the memory cap and the MemAvailable kill, one landed change per experiment, the refactor-first and land-a-replacement rules in `rules/experiment.md` (a refactor lands by the same criteria), and nothing outside the project tree, its linked repos, and lx-work changes. Rules, cards, and tolerances stay untouched; a problem with them goes to FEEDBACK.md.

## Step 1: onboarding without the discussion
`rules/onboarding.md` step 1 as written: setup, reading, MAP.md, knowledge/, the harness. Step 2's items come from the code, the deployment files, and the defaults above instead of the discussion, recorded as such. Quality is not discussed: the accuracy standard is the unmodified code's own outputs, frozen in the pass's environment, with L0 the only accepted level; verify grades every change L0 to L3 anyway, so the user can judge the parked ones.
- Baseline speed: the unmodified code in the image production runs, on the production GPU, three runs (the run-image tool), with the time breakdown and the noise floor measured there. When the production GPU is not this machine, run every A/B where the harness runs, and confirm on the production GPU as the last catalog step.
- Metric: end-to-end latency and the stage breakdown, nothing else, unless the deployment files show a throughput service.
- A shared production GPU runs other people's jobs: before each measurement there, check `nvidia-smi` for other processes, wait and retry instead of measuring beside them, record the busy periods, and lock the clock as far as permissions allow.
Then the phase is optimizing, and the catalog is the queue in trials/INDEX.md in the order below, one row per item with its evidence from MAP.md: the stage's time in milliseconds, not its share. A stage below the noise floor is skipped with that number as the reason; absolute times keep the decision stable when the engine ladder later shrinks the model's time.

## Step 2: the catalog, in order
Kept items stack: each starts from best, the baseline commit plus the kept patches, so the chain is the delivered code. Parked items start from the current best too and are measured against it. The engine ladder is the one place where parked trials build on each other: each rung's patch holds the whole ladder below it, so the user adopts one rung and gets all of it.
1. Environment: the project in the target image's environment (production's current image and the local environment built from it, `local/site.md`), with the code changes it needs to run there and nothing more. It is kept whatever the speed, since the user set the target; its speed against the production image, and its outputs' level against outputs dumped there when the run-image tool can dump them, open the report. A project already on the target image has no such item.
2. Redundant work, one experiment per finding, largest time first: computation repeated or unused, repeated initialization and model reloads, CPU/GPU round trips, syncs, full-array temporaries, repeated resize or cast (skill `perf-torch-sync-free`; cards `playbook/data/numpy-temporaries.md`, `playbook/data/pack-model-input.md`, `playbook/transfer/batched-copy-back.md`). Clear this before the engine, so the ladder measures the model and not the glue.
3. The engine ladder, built and timed on the production GPU, since tactics and precision support differ per compute capability. Rungs: TensorRT FP32 (it separates the graph optimization's gain from the precision's), FP16, then INT8 and FP8 only with calibration data, the calibration on a bounded sample under the memory cap with its peak estimated first (CLAUDE.md); FP8 only through an explicit quantization flow, worth it for transformer blocks, while a CNN takes INT8. Each rung uses the production builder settings (`playbook/env/trt-builder-level.md`) and the shape policy production needs (`playbook/serving/dynamic-batch-profiles.md`), and passes the MPS scan (`playbook/serving/mps-grid-barrier.md`) before it is parked or kept. On the production precision (FP16 when production has no engine yet): redundant and fusable layers (export cleanup, constant folding, the norm and attention plugins of the playbook's compute section), then CUDA graph of the enqueue (`playbook/host/cuda-graph-trt.md`). A project already on a TensorRT engine skips the rungs it has.
4. Input side: JPEG or PNG decode on the GPU or in hardware (`playbook/data/gpu-jpeg-decode.md`, `playbook/data/gpu-png-decode.md`). A decoder's outputs usually differ from the CPU library's, so this is normally parked with its level; `local/site.md` lists what was measured on this machine.
5. Preprocessing on the GPU up to the model input, one copy to the device, with the exact replicas the site lists where the contract fixes the arithmetic (`playbook/data/gpu-preprocessing.md`, `playbook/data/exact-resize-on-gpu.md`, `playbook/host/fused-preprocess-kernel.md`). A stage left on the CPU gets a line in NOTE.md with the measurement behind it: its time, and the transfer it would cost.
6. Postprocessing on the GPU from the model output, only compact results copied back (`playbook/transfer/roi-only-upload.md`, `playbook/transfer/batched-copy-back.md`), and encoding on the GPU where the output is an image and the site lists a library for it.
7. What still runs eagerly above the noise floor: CUDA graphs (skill `perf-torch-cuda-graphs`), then `torch.compile` as the last and least promising trial (`playbook/compute/torch-compile.md`), assessed as `rules/experiment.md` step 2 says.
Every item: `exp.sh new` or `exp.sh try`; Evidence, Hypothesis, and Plan in NOTE.md as if the user would read them, since the user asked that every choice have enough reason behind it; candidates in candidate/; verify and an A/B of at least three rounds; then keep, park, or drop (`rules/experiment.md` steps 3 to 5, `rules/self-iteration.md` for parking). Timebox: 90 minutes of your own work per item, a build or calibration what its estimate says; past it, park what works or drop it with what was learned, and queue the rest as a day task.
Last: the structure pass of `rules/wrap-up.md` over the kept chain, landed as one more experiment when it finds something; and when the production GPU is not this machine, the kept chain and every parked rung benched there, three runs each, in the image production runs. An item that loses its gain there is reported as such, and the user decides.

## Ending and the report
`exp.sh check` passes; STATUS.md "In progress" is none and "Waiting for the user" says `standard pass <date>: N kept, M parked, K skipped; report it (rules/standard-pass.md)`; commit lx-work. Then one reply, not a file: the kept chain as one table in order, each item's gain (the A/B's medians and change) and level; the parked items as `rules/self-iteration.md` reports them (best first, the A/B against its base, the level, what to decide; the ladder as rungs with cumulative numbers); one line per skipped item with its measurement; the defaults taken; the environment item's numbers; the production-GPU confirmation; the entries under "Waiting for the user". The user then adopts parked items (`exp.sh adopt`), changes defaults, or says the project is done; from there the ordinary loop applies.
