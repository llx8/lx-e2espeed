# Changelog

## 2026-10-21: the load test in one run: soak, worker restarts, log scan, memory per process
- rules/wrap-up.md and templates/tools/load-test/main.py: no production worker count anywhere; each image climbs the worker count (1, 2, 4, 8, 12, 16) until throughput stops growing, clients = workers and 2x at each count; then `--soak` (600 s at the delivered peak count, memory start against end), worker restarts counted from new PIDs, the container log scanned (tracebacks or a missing MPS daemon fail), GPU memory per process sampled, P90 added; about 35 to 40 minutes, a rerun repeats the failed part only.
  Why: the user (2026-10-21): the load test asks how well the algorithm uses the server (at how many workers the GPU peaks), production's worker count is operations' business; one run must leave nothing to rerun, and it must not take hours. An earlier version anchored the sweep and the soak on a production count.
## 2026-10-20: load test sweeps the worker count and judges saturation and memory
- rules/wrap-up.md, Deliver: the load test also sweeps the worker count and reports where throughput peaks; at the delivered image's peak one side must saturate (GPU utilization or power, a worker near 1.0 core, all host cores) or the test fails until the wait is found; GPU memory at the peak must be within 20% of the one-worker peak times the worker count and steady across levels, else the growing allocation is found first. templates/tools/load-test/main.py: `--workers` (WORKER_CONFIG mounts the image's config with each count) and the printed verdicts.
  Why: the user (2026-10-20) asked whether the rules say at how many workers the GPU peaks, that an unsaturated GPU at the peak needs its cause found, and that an abnormal GPU memory peak does too; they did not, and ops' load tests judge exactly these.

## 2026-10-13: landed optimizations must not bloat the project
- The user (2026-10-13): after an optimization lands, judge whether the project needs a refactor, so the additions do not swell its files. Agreed with the problem, not with the cadence: each kept patch is the smallest change that keeps interfaces, and several of them pile the old path, a fallback switch, the derivation, and the scaffolding into one file (one project's review ended in exactly such a refactor: the inference class split into stages, the CPU reference moved to acceptance code, the derivation to docs). A judgment after every experiment costs a verify and a bench each time and gets skipped. So `rules/experiment.md` Plan gets a refactor-first trigger (third patch on one function, or a structure the code lacks), Land and decide gets "land a replacement, not an addition", and `rules/wrap-up.md` Deliver turns its one line into a structure pass with the smells to look for. A refactor is always its own experiment with equal speed shown, and someone else's module gets a proposal, not a refactor.
