## 2026-10-13: landed optimizations must not bloat the project
- The user (2026-10-13): after an optimization lands, judge whether the project needs a refactor, so the additions do not swell its files. Agreed with the problem, not with the cadence: each kept patch is the smallest change that keeps interfaces, and several of them pile the old path, a fallback switch, the derivation, and the scaffolding into one file (one project's review ended in exactly such a refactor: the inference class split into stages, the CPU reference moved to acceptance code, the derivation to docs). A judgment after every experiment costs a verify and a bench each time and gets skipped. So `rules/experiment.md` Plan gets a refactor-first trigger (third patch on one function, or a structure the code lacks), Land and decide gets "land a replacement, not an addition", and `rules/wrap-up.md` Deliver turns its one line into a structure pass with the smells to look for. A refactor is always its own experiment with equal speed shown, and someone else's module gets a proposal, not a refactor.
